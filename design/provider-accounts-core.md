# Provider Accounts Core

Status: Companion specification for
[Provider Accounts, Browser Sessions, and Cursor Model Usage](./provider-accounts-browser-sessions-cursor-history.md).

## Module Boundaries

    Existing UI / Timer / CLI / Local HTTP
                       |
                       v
               ProviderAccounts
        view()                 perform()
          |                        |
          |        +---------------+---------------+
          |        |               |               |
          v        v               v               v
    Active Output  Provider        Browser         History
    Projection     Adapters        Session Broker  Scheduler
                       |               |               |
                 QuickJS plugin    sweet-cookie    Cursor ledger
                 or legacy Adapter sidecar         Adapter
                       |
                       v
              Credential Lease + Identity Claim

The Module is implemented in Rust. React receives only nonsecret views and typed operation
receipts. QuickJS receives a scoped connection target, never the account registry.

## Dependency Seams

- Provider account reconciliation is in-process. It is tested through the ProviderAccounts
  Interface without exposing its internal maps.
- JSON stores and the installation-key Keychain are local-substitutable dependencies. Production
  uses safe files and the existing macOS Keychain implementation; tests use temporary stores and
  an in-memory Keychain Adapter.
- The cookie helper is a local-substitutable process dependency. BrowserSessionBroker owns a
  fixed-process runner Adapter; tests replace it with a protocol fake.
- Cursor and Claude endpoints are true external dependencies. The provider Modules receive a
  metadata-only transport port with a fixed-origin production Adapter and scripted test Adapter.
- QuickJS is an existing runtime Adapter. Account routing is injected through one opaque lease;
  plugin callers do not learn the registry or persistence Interfaces.

These are internal seams. ProviderAccounts keeps the two-operation external Interface so UI,
timer, CLI, and Local HTTP callers do not have to coordinate identity, storage, or transport.

## Interface Types

    ProviderId = existing plugin ID
    AccountId = random UUID generated by OpenUsage
    ConnectionId = random UUID generated by OpenUsage
    BrowserCandidateId = random, memory-only ID with a short TTL

    AccountSelection =
      | Auto
      | Pinned(AccountId)

    OperationStatus =
      | Succeeded
      | Partial
      | Failed

    ProviderAccountView {
      providerId
      selection
      activeAccountId?
      accounts: AccountSummary[]
      persistenceWarning?
    }

    AccountSummary {
      accountId
      label
      runtimeHint?
      availability
      connectionKinds
      selected
      stale
      lastUpdatedAt?
    }

    BrowserCandidateSummary {
      candidateId
      browser
      profileLabel
      maskedHint?
      existingAccountId?
      expiresAt
    }

runtimeHint is generated from the current verified response and is not persisted. The default
persistent label is Account 1, Account 2, and so on. A user can rename it. If the user chooses
to put personal information in that label, it is an explicit user action.

RenameAccount trims the label, accepts 1 through 64 visible characters, and rejects control
characters and line breaks. Partial is a visible result reserved for operations such as an
explicit All Profiles scan or local discovery where some requested sources were unavailable. It
never means a failed identity or history check was treated as success.

## Operations

    ProviderOperation =
      | RefreshActive
      | SelectActive(AccountId)
      | FollowDefaultConnection
      | RenameAccount(AccountId, label)
      | ListBrowserProfiles(browser)
      | DiscoverBrowserSessions(browser, profileScope)
      | AttachBrowserCandidate(BrowserCandidateId)
      | DetachBrowserConnection(ConnectionId)
      | LoadHistory(AccountId, window)

Each receipt contains an operation ID, final status, the latest ProviderAccountView, and an
operation-specific result. Errors are logged with a correlation ID and returned to the UI as
short, actionable messages. There is no success-shaped silent fallback.

The Tauri commands expose the same shape:

    get_provider_account_view(providerId)
    perform_provider_account_operation(providerId, operation)

Frontend invoke arguments use camelCase. Account IDs are opaque; the frontend never constructs
or interprets them.

Successful mutations emit provider-account-view-changed with providerId and a monotonic revision;
the frontend then reads the new view. The event carries no label, identity hint, connection
locator, or credential. Existing probe-result events keep their current PluginOutput shape.

## Provider Account UI

Provider remains the navigation entity. Account controls appear only on detail pages whose
manifest declares accountSupport.

- The provider header shows the active account label and availability in a compact selector.
- The selector lists Auto and known accounts. Selecting an account performs SelectActive; choosing
  Auto performs FollowDefaultConnection.
- Manage Accounts shows connection kinds, stale or unavailable state, rename, Add Browser Account,
  and browser detach. It does not expose Cookie names, paths, raw identity, or token source details.
- Add Browser Account is a two-step browser/profile scan followed by candidate attachment. A
  mismatched Claude browser identity is explained but cannot create a browser-only Claude account.
- Overview, tray, notifications, CLI, and Local HTTP API v1 continue to show only the active
  provider projection. There is no All Accounts total in this release.
- Account switch, attach, detach, loading, stale, partial-refresh, identity-changed, and persistence
  failures all have distinct visible states. Errors include a correlation ID but no secret data.

## Persistence

provider-accounts.json stores a version, monotonic revision, and provider map. Each provider stores
Auto or Pinned selection plus accounts keyed by AccountId. Each account stores its user label,
identity namespace, HMAC fingerprint, and connections. A connection stores ConnectionId, kind,
and only a nonsecret locator; a browser locator is browser plus canonical profile key. Runtime
availability, raw paths, store IDs, subjects, and credential-generation values are not persisted.

provider-account-snapshots.json stores the existing compact cached snapshot payload per ProviderId
and AccountId: plan, lines, display name, and fetched time, without icon data.
provider-history/provider/account.json stores only complete aggregates. Each new JSON document
starts at schema version 1.

usage-api-cache.json stays at version 1 as the active provider projection. Existing data remains
displayable but is never guessed into an account. The first identified probe seeds the new
account snapshot and refreshes the v1 projection. Legacy plugins remain v1-only.

The migration is additive. An installation with no account registry creates one only after the
first identified account observation. A previous application version ignores the new files and
continues reading usage-api-cache.json. A failed account-store migration never rewrites or deletes
the v1 cache. No feature flag or compatibility shim is required.

All app and CLI writers reuse the cross-process lock and safe-replace pattern, merging at
ProviderId and AccountId granularity. Corruption is retained for diagnosis and surfaced as a
friendly persistence warning. No store contains raw events, credentials, browser database paths,
raw identities, or organization names.
